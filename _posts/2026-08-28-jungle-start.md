## 정글에 오기까지

### 개발을 못하는 전공자

14~15년. 중학교 때, 첫 프로그래밍 언어 C를 접했다. 터미널에 띄워진 나의 숫자, 글자들이 내가 원하는 대로 작동하고 움직이는 것을 보고 "개발자가 되어야겠다" 라고 결심했었다.

당시에 프로그래밍을 공부한다하여 구글에 "로드맵"을 검색하면...

```
"C언어를 먼저 공부하시고, 그 다음에 C++, Java, 자료구조&알고리즘..."
```

어렸던 나는 곧이곧대로 C언어 문법을 떼고 C++, Java...자료구조&알고리즘은 맛만 보고 바로 발을 뗐다. 나에게 가장 익숙했던 건 오로지 `#include <stdio.h>` 였다.

고등학교 때는, "지금 프로그래밍을 공부하기 보다, 좋은 대학에 가서 열심히 공부해보자!" 하는 마음으로 개발 공부는 잠시 두고 학업에 열중했다. 아마도...

그렇지만, 대학교에 오고 개발을 열심히 공부하겠다는 마음가짐은 그리 오래 가지 않았다. 막 코로나가 퍼지던 시기이도 했고 무엇보다 학부 강의는, 내가 생각했던 개발과는 정말 거리가 멀어보였다. 3학년, 4학년, 복무...6년을 허송세월했다고 지금도 솔직히 생각하지 않는다고 하면 거짓말일 것이다. 그렇게 공부를 놓고 게임이나 하면서 놀다가 사회복무 후, 마지막 학기를 시작했다.

### 인생에서 첫 팀프로젝트

"소프트웨어 공학" 수업. 첫 팀플이었다. 한 학기 동안 웹서비스 하나를 팀 단위로 만들어보고 기획과 발표를 해야 한다. 강의계획서를 제대로 안 보고 수강 신청한 내 잘못이다. 어쩌지, 나는 이제 막 복학했고, 무엇보다 나는 웹 개발이 너무 싫은데...Next.js? FastAPI? RESTful? AWS? Docker? Redis? 이미 우리 팀 4명 중 한 명은 얼굴도 못 봤다. 수강신청 변경 기간에 바꿔버리고 도망갔나보다.

`그렇다고, 아무것도 모른다고 어영부영 팀에 묻어가고 싶지 않다.`

그나마 나에게 남은건 사회복무를 하면서 깊게 느꼈던, "절대 힘들고 하기 싫다고 피하기만 하는 것은 인생에 아무런 도움이 되지 않는다" 라는 마음가짐이었다. 클로드 코드를 결제하고 팀원의 의견을 복붙하며 깃 사용법을 익히고 협업해나갔다. 기능 하나 할 때마다 이슈를 남기고 개발을 하며 "뒤처지면 어쩌지, 짐덩이라고 생각하면 어쩌지" 라는 마음에 하루에 PR을 5개를 달기도 했다. 

`지금 생각하면, 그건 팀에게 별로 도움이 안 되었다고 자신있게 말할 수 있다. 쓰레기가 들어가면, 쓰레기가 나온다.`
### 격차, 자괴감, 그리고 나 자신에 대한 실망

이 팀프로젝트 경험은, "이렇게 살면 안되겠다. 공부를 해야겠다." 라고 느낀 계기가 되었다. 팀원 중 한 명이 실력, 협업 지식, 인프라 지식, 도메인, AI...정말 많은 것을 알고있었고, 우리 팀을 이끌어나갔다. 나는 여기서 정말 "이 사람은 나랑 같은 학년인데 이렇게나 잘 알고, 팀을 이끌어가며 발표도 잘하고, 경험도 많은데 나는 뭐지? 내가 내세울 수 있는건, 내가 할 수 있는건 뭐지?" 라는 생각밖에...들지 않았다. 같은 학교, 같은 학부생인데 이렇게나 차이가 나다니. 너무나도 헛살았다. 

`"내가 여기, 컴퓨터공학과에 온 이유가 뭘까?"`

단지 취업을 하고 싶어서? 컴퓨터공학과가 뜨니까? 전부 아니었다. 중학교 시절 LLM이 없어도, 블로그에 적힌 코드가 5년전 코드여도, 자료가 영어뿐이어도, 결과물이 아무것도 아닌 터미널에 글자 띄우는 것이어도, 
내 손으로 무언가를 만들고 움직일 수 있다는 게 그때는 정말 즐거웠었기에.

## 추상화의 늪에서

### 다시 시작한 공부

`남은 학기지만, 제대로 공부해보자`

쉽지 않았다. 데이터통신, 데이터베이스프로그래밍(Spark), 소프트웨어공학, 컴퓨터그래픽스. 마지막 4개의 수업이었다. 데이터베이스프로그래밍은 SQL을 생각하고 들어갔으나, 분산 데이터베이스에 관한 내용일 줄은 몰랐고. 소프트웨어공학은 팀프로젝트에 기말고사까지. 컴퓨터그래픽스는...코딩이 아니라 "그래픽스에 쓰이는" 각종 수학 원리와 증명을 배우는...수업이었다.

하지만, 데이터통신 수업은 달랐다. 오히려 데이터통신 수업은 수강 신청 전부터 정말 평가가 극단적으로 갈리던 수업이었다. 

`"여러분들이 주어진 문제 상황에서 "나는 TCP를 선택하겠다.", "아니다. 나는 UDP를 선택하겠다." 를 이해가능하고 정당한 근거와 함께 명확히 설명할 수 있으면 TCP를 선택하든 UDP를 선택하든 모두 맞게 할 겁니다. 다만, 근거가 명확하지 않다면 어떤 걸 선택하든 오답처리합니다."`

수업 내용은 네트워크 수업의 근본 서적인 "Computer Networking: a Top-Down Approach" 내용을 바탕으로 진행되었다. 그렇지만, 수업의 방식은 달랐다.

`"여러분들은 "문제"를 잘 봐야합니다. 기술의 발전은 언제나 "무엇이 불편한가?, 무엇이 문제인가?" 에서 출발합니다."`

교수님께서 설명하셨던 방식을 기억으로 재구성해봤다.
```
HTTP/1.0 에서는 1개의 요청 당 기본적으로 1번의 연결을 해야했다. 
파일이 10개가 있으면 10번을 계속 연결을 끊고 새로 맺어야했다. 
이 불편함 때문에  "지속 연결" 개념을 기본으로 한 것이 HTTP/1.1 이었다.

HTTP/1.1 에서는 HOLB 문제가 터졌다. 
한 연결에서 여러 개의 데이터를 보낼 때 순서대로 보내야했는데, 
이때 앞의 데이터 전송이 막히면 뒤의 데이터들은 앞의 데이터가 나갈 때 까지 계속 기다려야한다. 
이 불편함 때문에 "멀티플렉싱" 기술을 도입해, 
보내는 건 한 번에 여러 개로 순서없이, 받는 건 순서대로 조립하는 방법을 도입한 것이 HTTP/2 였다.

HTTP/2에서는 근본적인 문제가 터졌다.
HTTP 계층에서는 막히지 않는데, 문제는 TCP였다.
패킷이 하나라도 Drop되면, 그 패킷을 재전송받아 순서를 맞출 때까지 
같은 TCP 연결 위의 HTTP/2 스트림들을 일시 정지해야했다. 

여기서 구글이 등장한다. 
"전 세계 트래픽 상당수가 우리 서비스인 유튜브, 구글 검색인데 왜 TCP 때문에 답답하게 통신해야하지?". 

그렇다고 TCP의 프로토콜은 수정하기에는 애초에 OS 깊숙이 박혀있는 프로토콜을 수정하고, 
전 세계가 그걸 업데이트 하기 까지 어느 정도의 시간이 걸릴 지 모르니 매우 어려운 문제였다.

구글은 여기서 생각을 바꾼다.
"UDP를 써보자."

이들은 TCP가 아닌, UDP에 집중했다. 
하지만, UDP는 "일단 던지고 보는" 프로토콜이 아닌가? 
그래서, UDP 위에 직접 로직을 올렸다. 
첫 패킷에 연결, 암호화, 데이터를 다 때려 박고 신뢰성 검증 로직도 올렸다. 
이것이 **QUIC**이며, 이 위에 HTTP의 의미를 올린 것이 HTTP/3이었다.
```

물론 실제 발전 과정은 이것보다 훨씬 복잡하겠지만, 당시 내 머릿속에는 대략 다음과 같은 흐름으로 들어왔다.

`"여러분들은 공부할 때, 무작정 외우지 마시고 언제나 왜? 라는 질문을 던져보세요. 왜 만들었지? 무엇이 불편해서? 왜 그렇게 했지? 단지 외우는 것은 아무 도움이 안됩니다."`

이 수업은 나의 공부 방식, 그리고 왜 그렇게 전공 공부가 싫었는지 충격으로 다가왔다. 그냥 외우려고 하니 "이걸 내가 왜 외워야하지...이게 뭔데" 라는 생각이 들었고. 강의에서는 "이게 이렇습니다" 하니 그냥 외우게 되고. 결국 무의미한 루프때문에 금방 흥미가 식었었다. "내가 생각한 공부는 이게 아닌데..."

### 바퀴를 재발명해보다

"Build Your Own x"

나는 아래의 동작 원리를 한 번 직접 만져봐야, 그 위의 설명도 뒤늦게 감이 오는 편이다. 일종의 Bottom-Up 인간이다. 하지만 부끄럽게도, 나는 OSI 7 Layers 구조가 "진짜" 나누어져 있는 줄 알았다. TCP는 TCP고, HTTP는 HTTP로 뭔가 "네트워크 계층을 거쳐서 전송 계층, 그리고 표현, 응용 계층..." 적인 느낌이 있지 않았나...? 나만 그랬던 건가...

이 생각은 CodeCrafters의 Build Your Own x 프로젝트를 직접 해보면서 깨졌다.

Build Your Own HTTP Server 첫 단계에서는 다음과 같은 걸 구현한다.
1. 포트를 바인딩하고 (소켓)
2. 무언가 오면 `HTTP/1.1 200 OK\r\n\r\n` 이라는 String을 보내야한다.

그 다음 단계에서는
1. `GET /index.html HTTP/1.1\r\nHost: localhost:4221\r\nUser-Agent: curl/7.64.1\r\nAccept: */*\r\n\r\n` 등의 요청에서
2. 경로를 알아내서 200, 또는 404를 보내야한다.

그 다음 부터는
```
POST /files/number HTTP/1.1
Host: localhost:4221
User-Agent: curl/7.64.1
Content-Type: application/octet-stream
Content-Length: 5

12345
```

이런 "바이트" 들이 들어오면 하나하나 해석해서 무엇을 요청하는 건지, 헤더는 맞게 왔는지, 내용은 헤더에 맞는지 등을 알아낸다.

아래는 그때 당시 작성했던 코드 중 일부다.

```go
func parseRequest(reader *bufio.Reader) (request, error) {
    line, err := reader.ReadString('\n')
    if err != nil {
        return request{}, err
    }

    fields := strings.Fields(line)
    if len(fields) != 3 {
        return request{}, fmt.Errorf("malformed request line")
    }

    req := request{
        method:  fields[0],
        target:  fields[1],
        headers: map[string]string{},
    }

    for {
        line, err := reader.ReadString('\n')
        if err != nil {
            return request{}, err
        }

        if line == "\r\n" { // 빈 줄부터 본문이 시작된다.
            break
        }
        name, value, ok := strings.Cut(line, ":")

        if ok {
            req.headers[strings.ToLower(strings.TrimSpace(name))] = strings.TrimSpace(value)
        }
    }
    if value, ok := req.headers["content-length"]; ok {
        length, err := strconv.Atoi(value)
        if err != nil || length < 0 {
            return request{}, fmt.Errorf("invalid content-length")
        }

        // Read는 짧게 끝날 수 있으므로 선언된 본문 길이를 모두 채운다.
        req.body = make([]byte, length)
        if _, err := io.ReadFull(reader, req.body); err != nil {
            return request{}, err
        }
    }
    return req, nil
}
```

func routeRequest(req request, directory string) response {
    switch {
    case req.method == "GET" && req.target == "/":
        return response{status: 200}
		
    case req.method == "GET" && strings.HasPrefix(req.target, "/echo/"):
        return response{
            status:      200,
            contentType: "text/plain",
            body:        []byte(strings.TrimPrefix(req.target, "/echo/")),
        }
    case req.method == "GET" && req.target == "/user-agent":
        return response{
            status:      200,
            contentType: "text/plain",
            body:        []byte(req.headers["user-agent"]),
        }
    case req.method == "GET" && strings.HasPrefix(req.target, "/files/"):
        body, err := os.ReadFile(filepath.Join(directory, strings.TrimPrefix(req.target, "/files/")))
        
		if err == nil {
            return response{status: 200, contentType: "application/octet-stream", body: body}
        }
    case req.method == "POST" && strings.HasPrefix(req.target, "/files/"):
        path := filepath.Join(directory, strings.TrimPrefix(req.target, "/files/"))
        if os.WriteFile(path, req.body, 0644) == nil {
            return response{status: 201}
        }
    }
    return response{status: 404}
}

작동 방식은 정말 간단하다.
1. 소켓에서 바이트가 흘러들어온다.
2. 줄바꿈 기준으로 바이트를 한 줄씩 끊어서 읽는다. (이때 버퍼링해서 읽는다. TCP는 메시지나 줄의 경계를 제공하지 않는 바이트 스트림이기 때문이다)
3. 그에 맞게 if 분기로 응답을 한다.

놀랐었다. 

`"HTTP가 무언가 뾰로롱하는게 아니구나. 그냥 연결위에 GET /index HTTP/1.1\r\n.... 어쩌고 보내면 그게 HTTP구나. 그리고 그걸 해주는게 지금까지 내가 써왔던 HTTP 라이브러리가 대신 해주고 있었구나". "요청을 파싱해서 Target을 알아내고, 그걸 찾아서 반환하는게 라우터였구나. 그리고 그게 @app.route가 해주고 있었던 거구나."`

Build Your Own Redis의 RESP Parser 구현은 더 신기했다(아직 초반이지만). 
`"꼭 HTTP처럼 안보내도 되는구나. 그냥 서로 같은 해석 규칙에 합의하기만 하면, HTTP와 다른 형태의 프로토콜도 만들 수 있구나."`

`"HTTP는 그냥, 네트워크 바이트스트림 위에 올려진 문자열 또는 바이너리 파싱 규칙이며, 우리는 그 규칙으로 해석하고, 규칙으로 보내는 거였구나."`

### 장막의 한 귀퉁이를 들추고

어쩌면 나는 “추상화의 늪”에 빠진 게 아닐까? 물론 추상화가 나쁜 것은 아니다. 추상화가 있으니 나는 매번 소켓부터 다시 만들지 않고도 서비스를 만들 수 있다. 가장 문제였던 건,

`내가 빠졌던 늪은 추상화 그 자체가 아니라, 아래에 무엇이 있는지 한 번도 본 적 없는 채 그 위의 이름만 외우고 있던 상태였다.`

 사실, 아직도 나는 길을 못 찾았다. 그 길을 찾으려고 정말 여러 분야를 건드려봤다. 리버싱, 악성코드 분석, ML/DL, 웹, 시스템 프로그래밍, 임베디드 프로그래밍...

하지만 금방 흥미를 잃고, 단지 "경험 해봤음" 사람이 되었다. 여러 분야를 건드려보기는 했지만, 어느 하나도 깊이 파고들었다고 말하기는 어려웠다.

그렇지만 느낀건 있었다.

`"아래에 뭔가 있구나"`

내가 본 것은 어느 분야의 전부도, 본질도 아니었다. 그저 우연히 들춰 본 장막의 한 귀퉁이였다. 그래도 그 짧은 순간마다, 내가 사용하던 이름 아래에 무언가 구체적인 것이 실제로 돌아가고 있다는 사실은 보였다.

HTTP 라이브러리의 장막 아래에는, 바이트를 읽고 해석하는 코드가 보였고.
악성코드의 장막 아래에는, 백신한테 걸리지 않으려 다른 프로세스의 메모리를 파고 들어가는 움직임이 보였었고.
ML/DL의 장막 아래에는, 답을 함수로 근사하려는 코드가 보였었고.
그래픽스의 장막 아래에는, 좌표와 행렬로 화면을 그리는 수학이 보였었다.

내가 매일 사용하던 이름들 아래에는,
누군가가 실제 문제를 해결하기 위해 만든 구체적인 무언가가 있었다.

`"다 만들어진 이유가 있었구나."`

## 그래서 정글에 오게 되었다.

무언가를 깨우쳤기 때문은 아니다. HTTP 서버 하나를 만들어보고, 수업 몇 개를 들었다고 내가 컴퓨터과학의 밑바닥을 다 이해했다고 말할 수는 없다. 오히려 반대였다. 내가 안다고 생각했던 것들이 사실은 이름뿐이었다는 걸 알게 되었고,

그 이름 아래에 아직 내가 모르는 것이 훨씬 많다는 것도 알게 되었다.

내가 본 건 장막 전체가 아니라 한 귀퉁이였다. 그런데 이상하게도, 그 작은 틈을 보고 나니
이번에는 도망가지 않고 조금 더 안쪽으로 들어가 보고 싶어졌다.

과정을 수료한 뒤의 나는 어떤 "개발자"의 모습으로 서있을지는 아직 잘 모르겠지만, 어디가서 당당히 "개발자입니다." 라고 말할 수 있는 사람이 되어있었으면 좋겠다.
