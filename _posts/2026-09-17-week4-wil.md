이번 주는 공부와 학습을 떠나서, 나 자신에게 아쉬웠던 부분이 정말 많았고, 후회도 했던 한 주 였다. 그래도, 과거에 연연하지 않고, 잘못을 인정하고, 한 층 성숙해지는 기회의 발판으로 생각해야겠다.
4주차는 자료구조와 C. 중학생 때 C를 처음 배웠던 때가 생각이 났던 주차였다. 그때는 이중 포인터니 구조체니 공용체니 그냥 그런 문법이 있나보다...했었지만, 확실히 여러 가지를 건드리고 다시 해보니 "그래서 그랬구나" 싶었던게 꽤 많았었다. 이번 WIL에서는 내가 이해한 얕은 지식들을 어느정도 풀어서 설명하겠다.
## 자료구조와 메모리

> "칠판과 칸, 그리고 데이터"

사실 메모리는 하나의 거대한 **"칠판"** 이다. **"칠판"** 에는 저장할 수 있는 **"칸"** 들이 엄청나게 많이 있으며, 각 **"칸"** 들에는 **"데이터"** 를 저장할 수 있다.

중요한 건, 메모리는 그 데이터가 본질적으로는 **뭐가 뭔지 모른다**. 정수형인가? 부동소수점으로 표현되나? 문자열인가? 포인터인가? 메모리에는 이 값의 타입 정보가 붙어있지 않다.

CS:APP 의 1장에서 나왔던 것처럼, CPU에 들어가서, 프로그램의 **문맥**으로 판단한다. 칸에 들어있는 16진수 바이트 값, 비트 값 "0100 0001", 즉 "0x41" 를 **숫자 65로 판단할 지, 문자 "A" 로 판단할지, 어쩌면 주소일지**. 

그리고 판단하는 것은 **프로그램이다**. 해당 값을 `int`형으로 해석할 지, `char` 형으로 해석할 지.

> "자료구조는 데이터를 이 거대한 칠판에 데이터들을 **어떤 규칙으로 배치**할지를 정한다."

1. 배열은 "연속된 칸" 들에 쭉 배치한다.
2. 리스트는 "떨어져 있는 칸 들을, **주소**를 이용해서" 연결한다.

메모리의 각 칸 들을 구분하기 위해서는 **"주소"** 가 필요하다. 일종의 "좌표" 다. 

사실 우리가 보는 `0x7FFFF...` 형태의 16진수 값은 해당 메모리의 주소 값을 사람이 읽기 편하게 바꾼 것이다. 그리고, 우리가 프로그램에서 보통 보는 주소는 **실제 메모리의 주소는 아니다**. OS가 프로그램에게 가상 주소 공간을 제공하고, **"물리 주소"** 가 매핑되어있는 페이지 테이블을 관리한다.

프로그램이 그 메모리에 접근하면 CPU의 MMU는 이 페이지 테이블을 쭉보고, **"가상 주소를 물리 주소로 변환"** 한다. 우리가 보는 프로그램의 주소 공간도 사실, **OS가 만들어준 거대한 가상 칠판**에 가깝다.

## 그리고 할당과 해제

> "내 데이터를 어느 칸에 써야하지?"

당연하지만, 컴퓨터는 현재 내 프로그램만 켜져 있는 상태가 아니다. 따라서 아무 칸이나 골라서 사용할 수는 없다. 이미 다른 데이터가 사용하고 있는 공간일 수도 있고, 애초에 내가 접근할 수 없는 공간일 수도 있다.

그래서 프로그램은 자신이 사용할 메모리 공간을 **할당**받아야한다.

C에서는 대표적으로 `malloc()`을 이용해 실행 중에 필요한 메모리를 동적으로 할당할 수 있다.

```c
int *arr = malloc(sizeof(int) * 10);
```

> "정수 10개를 저장할 정도의 칸이 필요해요!"

그러면 메모리 할당자는 현재 사용할 수 있는 공간 중에서 적당한 영역을 찾아주고, 그 공간의 **시작 주소**를 돌려준다.

```text
거대한 가상 칠판

[사용 중][사용 중][ 빈 공간 ][ 빈 공간 ][ 빈 공간 ][사용 중]
                    ↑
              "여기부터 쓰세요."
```

중요한 점은 `malloc()`이 데이터를 주는 것이 아니라, **데이터를 저장할 수 있는 공간의 주소를 돌려준다는 것**이다. 그래서 `malloc()`의 반환값 역시 포인터다.

```c
int *arr = malloc(sizeof(int) * 10);
```

여기서 `arr`에는 정수 10개가 들어있는 것이 아니다. 정수 10개를 저장할 수 있도록 할당받은 메모리 공간의 **"첫 번째 주소"** 가 들어있다. 이제 프로그램은 그 주소를 기준으로 데이터를 써나갈 수 있다.

```c
arr[0] = 10;
arr[1] = 20;
arr[2] = 30;
```

> "이제 더 이상 이 칸을 쓸 필요 없으니, 돌려드릴게요."

그런데 빌렸으면 돌려줘야 한다.

```c
free(arr);
```

`free()`는 우리가 사용하던 메모리 공간을 다시 사용할 수 있도록 **반납하는 것**이다.

여기서 처음에는 조금 이상하게 느꼈던 부분이 있다.

```c
int *ptr = malloc(sizeof(int));

*ptr = 10;

free(ptr);
```

`free(ptr)`를 했으니, 왠지 `ptr` 자체도 사라질 것 같았다.

하지만 그렇지 않았다.

`free()`가 없애는 것은 포인터 변수가 아니라, **그 포인터가 가리키던 메모리 공간에 대한 사용 권한**이다.

```text
free 이전

ptr
 |
 v
[ 10 ] <- 내가 사용 중인 공간

free 이후

ptr
 |
 v
[ ?? ] <- 해제되었으니...이제 내가 사용하면 안 되는 공간
```

즉 `ptr`이라는 변수 자체는 여전히 존재하고, 심지어 그 안에는 예전에 가리키던 주소 값도 그대로 남아있을 수 있다. 다만 그 주소의 메모리는 이제 **더 이상 내 것이 아니다.** 이 칸은 이후 다른 `malloc()`에게 다시 할당될 수도 있고, 전혀 다른 데이터가 들어갈 수도 있다.

그리고 여기서 조금 다른 문제가 시작된다.

```c
free(ptr);

printf("%d\n", *ptr);
```

포인터에는 주소가 남아있으니, 문법적으로는 다시 그곳에 접근할 수 있을 것처럼 보인다. 하지만 이미 내가 반납한 칸이다.

우리는 지금 **내 것이 아닌 칸을 다시 들여다보고 있는 것**이다.

## 그리고 포인터

> "어느 칸에다 써놨었더라..."

중학생 때 처음 C를 배울 때는 `*`, `**`, `&`가 나오기 시작하면 슬슬 정신이 혼미해졌다.

```c
int *p;
int **pp;
```

> "별이 왜 계속 늘어나지?"

그때는 그냥 **"포인터라는 특이한 문법이 있구나"** 정도로 외웠던 것 같다. 뭐 변수를 가리키고 있구나~

그런데 메모리부터 다시 생각해보니 포인터 자체는 생각보다 단순했다.

> **"포인터는 주소를 값으로 저장하는 변수다."**

```c
int a = 10;
int *p = &a;
```

`a`도 메모리 어딘가에 존재한다. 예를 들어 `a`가 `0x1000`이라는 주소에 있다고 가정해보자.

```text
주소        값

0x1000     10
```

`&a`는 이 `a`가 존재하는 위치, 즉 주소를 가져온다.

```c
&a = 0x1000
```

그리고 그 주소 값을 `p`에 저장한다.

```text
p <- 포인터 변수

주소        값
0x2000     0x1000
              |
              v
           a의 위치
```

이 말은 결국, **포인터도 변수다. 그러므로 포인터 역시 메모리 어딘가에 존재한다.**

위의 예에서 `p`가 `0x2000`이라는 주소에 존재한다고 생각해보면,

```text
  p                a
0x2000          0x1000
[ 0x1000 ] ---> [ 10 ]
```

가 된다. 그렇다면,

> "`p`도 메모리에 있는 변수라면, `p`의 주소도 있지 않을까?"

당연히 있다.

```c
&p
```

위의 예시라면 `0x2000`이다.

그리고 그 주소를 저장하면?

```c
int **pp = &p;
```

이중 포인터가 된다.

```text
    pp               p            a
[ 0x2000 ] ---> [ 0x1000 ] ---> [ 10 ]
```

예전에는 `int **pp`를 보면 뭔가 굉장히 특별한 문법처럼 느껴졌다.

하지만 결국은,

> 정수를 가리키는 주소를 저장한 변수가 `int *`이고,  
> 그 `int *` 변수의 주소를 저장한 변수가 `int **`다.

라는 이야기였다.


그저 **"주소를 저장한 변수의 주소"**일 뿐이었다.

---

그리고 다시 `free()` 이야기로 돌아가보자.

```c
int *ptr = malloc(sizeof(int));
*ptr = 10;

free(ptr);
```

`free()` 이후에도 `ptr` 안에는 예전에 할당받았던 주소 값이 남아있을 수 있다고 했다.

즉,
```text
ptr
 |
 v
[ 이미 해제된 공간 ]
```

이런 상태가 된다.

포인터는 여전히 어딘가를 가리키고 있는데, 그 대상은 이미 유효하지 않다. 이러한 포인터를 **Dangling Pointer**, 직역하면 **매달린 포인터**라고 한다.

더 큰 문제는 이 포인터를 다시 사용하는 경우다.

```c
free(ptr);

*ptr = 20;
```

이미 해제된 메모리를 다시 사용하는 것. 이것이 **Use-After-Free**, 줄여서 **UAF**다. 문제는 해제된 공간이 항상 텅 비어있는 것이 아니라는 것이다.

메모리 할당자는 그 공간을 나중에 다른 데이터에게 다시 줄 수도 있다.

```text
1. 처음

ptr
 |
 v
[ 내 데이터 ]


2. free(ptr)

ptr
 |
 v
[ 반환된 공간 ]


3. 다른 데이터가 다시 할당받음

ptr
 |
 v
[ 남의 데이터 ]
```

그런데 예전의 `ptr`을 가지고 다시 접근한다면? 예전 데이터를 건드릴수도 있고, 실제로는 **전혀 다른 데이터가 들어있는 공간을 수정하고 있을 수도 있다.** 그래서 UAF가 단순한 프로그램 오류를 넘어서 보안 취약점으로 이어질 수도 있다는 것도 이해하게 되었다.

자료구조는 데이터를 **어떻게 배치할 것인지**에 대한 규칙이고,
메모리 할당은 그 데이터를 저장할 **공간을 어떻게 얻을 것인지**에 대한 이야기이며,
포인터는 그 공간을 **어떻게 기억하고 다시 찾아갈 것인지**에 대한 이야기였다.
